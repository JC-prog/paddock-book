# Quickstart: Chat Provider Configuration

Validates FR-001–FR-015 / SC-001–SC-006 end-to-end. Steps 1–5 need only a
locally running backend + Postgres + Ollama (this project's existing
local-dev setup, README's "Running Fully Locally" section) — no AWS or
external API-key access required. Steps 6–7 are environment-dependent
(need real Bedrock/OpenAI-compatible access) and are optional to run
live; their logic is otherwise covered by unit tests with mocked clients.

## Prerequisites

- Backend running locally (`cd backend && uvicorn src.main:app --reload`),
  Postgres up, migration `db/init/005_chat_provider_config.sql` applied.
- An admin account (`python -m src.modules.admin.cli --promote-admin <email>`,
  per feature 012's existing bootstrap flow) and its access token.
- Ollama running locally with at least one model pulled (existing
  local-dev prerequisite, unchanged by this feature).

Set `TOKEN` to the admin's access token and `BASE=http://localhost:8000`
for the commands below.

## 1. Fresh install defaults to Ollama, zero configuration

```bash
curl -s -H "Authorization: Bearer $TOKEN" $BASE/v1/admin/settings/chat-provider
```

**Expected**: `{"active_provider": "ollama", ..., "openai_compatible_api_key_set": false}`.
Confirms FR-001 and the "works exactly as today, out of the box" default
from data-model.md.

## 2. A normal chat request still works, unmodified

Send a chat message as any authenticated (non-admin is fine) user via the
existing `/v1/chat` flow (frontend, or `POST /v1/chat`). Confirm a
streamed answer comes back, generated by the local Ollama model — this is
the pre-existing behavior, now flowing through the new dispatch in
`generation.py` rather than the old hardcoded path.

**Expected**: No behavior change from before this feature — confirms the
Ollama branch is a faithful refactor, not a regression.

## 3. Activation is blocked without required settings (FR-012, FR-013)

```bash
curl -s -o /dev/null -w "%{http_code}\n" -X PUT \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"active_provider": "bedrock"}' \
  $BASE/v1/admin/settings/chat-provider
```

**Expected**: `409` — no `bedrock_model` has been saved yet. Repeat with
`"active_provider": "openai_compatible"` — also `409` (missing base
URL/key/model). Confirms the activation-blocking rule without needing any
real Bedrock/OpenAI-compatible access — this is pure database-state
validation (research.md).

## 4. Configure and activate the OpenAI-compatible provider (credential entry, FR-004)

```bash
curl -s -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -X PUT -d '{
    "active_provider": "openai_compatible",
    "openai_compatible_base_url": "https://api.openai.com/v1",
    "openai_compatible_api_key": "sk-test-placeholder",
    "openai_compatible_model": "gpt-4o-mini"
  }' \
  $BASE/v1/admin/settings/chat-provider
```

**Expected**: `200 OK`, response includes
`"openai_compatible_api_key_set": true` and
`"openai_compatible_base_url": "https://api.openai.com/v1"` — but no
`openai_compatible_api_key` field with the actual value anywhere in the
response (FR-011). Confirms FR-004/FR-012's "all three together" save
path and FR-011's never-round-tripped guarantee.

## 5. Switching back to a previously configured provider doesn't require re-entry (FR-015)

```bash
curl -s -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -X PUT -d '{"active_provider": "ollama"}' \
  $BASE/v1/admin/settings/chat-provider
# ... then switch back:
curl -s -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -X PUT -d '{"active_provider": "openai_compatible"}' \
  $BASE/v1/admin/settings/chat-provider
```

**Expected**: The second call succeeds (`200`, not `409`) — the
credential saved in step 4 was retained across the switch away and back,
without being resent. Confirms FR-015 and the partial-update `PUT`
semantics (research.md).

## 6. (Optional, needs a real OpenAI-compatible endpoint + key) Live chat generation

Repeat step 4 with a real base URL/key/model, then send a chat message.

**Expected**: The streamed answer is generated by that service, not
Ollama — confirms SC-001/SC-002 (the very next chat request uses the
newly active provider) and the `openai.AsyncOpenAI` streaming bridge
(research.md) against a real endpoint.

## 7. (Optional, needs AWS Bedrock access) Live Bedrock chat generation

```bash
curl -s -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -X PUT -d '{"active_provider": "bedrock", "bedrock_model": "<a model id enabled on this AWS account>"}' \
  $BASE/v1/admin/settings/chat-provider
```

Then send a chat message.

**Expected**: A streamed answer generated via Bedrock's Converse API,
confirming the thread/queue async bridge (research.md) actually streams
correctly against a real Bedrock call, not just under mocks.

## 8. Frontend page (`/admin/chat-provider`)

Log in as an admin in the browser, navigate to `/admin/chat-provider`.

**Expected**: The page loads and shows the currently active provider
(User Story 3); selecting a different provider and saving updates it;
selecting the OpenAI-compatible provider reveals base URL/key/model
inputs; attempting to activate Bedrock or OpenAI-compatible without
required fields shows a clear inline error rather than a raw `409` body;
a previously saved API key is shown as present without its value ever
appearing in the page or in browser dev tools' network responses.

## Cleanup

```sql
-- Reset to the fresh-install default, if desired:
UPDATE chat_provider_settings SET
  active_provider = 'ollama',
  bedrock_model = NULL,
  openai_compatible_base_url = NULL,
  openai_compatible_api_key = NULL,
  openai_compatible_model = NULL
WHERE id = 1;
```
