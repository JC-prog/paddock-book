# Feature Specification: Chat Provider Configuration

**Feature Branch**: `016-chat-provider-config`

**Created**: 2026-08-12

**Status**: Draft

**Input**: User description: "Add an admin panel page where an operator can configure which LLM provider powers chat answer generation, which is currently hardcoded to Ollama with no provider abstraction at all. The new admin page must let the operator pick a provider (Ollama, AWS Bedrock, or an API-key-based provider such as OpenAI or Anthropic) and, for API-key-based providers, paste the API key into a text box and save it. The chosen provider becomes what chat generation actually uses for subsequent chat requests, without a code deploy. Admin-only. Persisted configuration must survive a backend restart. Out of scope: embedding-generation provider (has its own separate switch already), multi-provider fallback/failover, per-user provider preferences, and live validation of API keys at save time."

## Clarifications

### Session 2026-08-12

- Q: Does the admin need to specify which model to use for the active provider, or is the model fixed per provider and not configurable through this page? → A: A model-name field the admin fills in alongside the provider selection — required for Bedrock and the OpenAI-compatible provider, optional for Ollama (falls back to the existing default model setting when left blank).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Switch the active chat provider (Priority: P1)

An admin needs to change which LLM provider answers chat questions — for
example, moving from a local Ollama instance to a hosted provider — without
asking an engineer to change code and redeploy the application.

**Why this priority**: This is the core value of the feature. Without it,
there is nothing to build; every other capability exists to support this one
action.

**Independent Test**: As an admin, open the provider configuration page,
select a different provider that requires no additional setup (e.g. switch
between two already-configured providers), save, then ask a question in chat
and confirm the response was generated by the newly selected provider.

**Acceptance Scenarios**:

1. **Given** the admin is on the provider configuration page, **When** they
   select a different provider from the available list and save, **Then**
   the page confirms the change was saved and shows the new provider as
   active.
2. **Given** a provider change has just been saved, **When** any user sends
   a new chat message afterward, **Then** the answer is generated using the
   newly active provider, with no application restart or redeployment
   involved.
3. **Given** the backend process restarts (e.g. a routine deploy or crash
   recovery) after a provider was configured, **When** the application comes
   back up, **Then** the previously configured provider is still active.
4. **Given** the admin selects AWS Bedrock as the provider, **When** they
   enter a Bedrock model identifier and save, **Then** subsequent chat
   requests are generated using that specific model on Bedrock.

---

### User Story 2 - Configure the OpenAI-compatible provider (Priority: P1)

An admin needs to enable a provider that requires an API key — via a
generic OpenAI-API-compatible connection (a base URL, an API key, and a
model name, covering OpenAI itself, Anthropic-compatible proxies, and
other OpenAI-API-compatible services through one integration) — by
pasting that key (and entering its base URL and model name) into the
admin panel, so that provider becomes usable without any secret ever
being placed in server configuration files or environment variables by
hand.

**Why this priority**: Ollama and Bedrock can both work with zero
additional admin-supplied secrets (Ollama needs no key; Bedrock uses the
deployment's existing AWS credentials), but the OpenAI-compatible provider
cannot be activated at all without this capability — it's required for
that entire class of provider to be usable.

**Independent Test**: As an admin, select the OpenAI-compatible provider,
enter a base URL, an API key, and a model name, save, then confirm that
provider can be made active and that chat requests succeed using it.

**Acceptance Scenarios**:

1. **Given** the admin selects the OpenAI-compatible provider, **When**
   they enter a base URL, paste a value into the API key field, and
   specify a model name, and save, **Then** the base URL, key, and model
   name are stored together as that provider's credential.
2. **Given** the OpenAI-compatible provider has a previously saved
   credential, **When** the admin returns to the configuration page
   later, **Then** the page shows the saved base URL and model name and
   indicates a key is already saved, without displaying the key's
   plain-text value.
3. **Given** the OpenAI-compatible provider has never had a credential
   saved for it, **When** the admin tries to activate it as the current
   provider without providing a base URL, key, and model name, **Then**
   the system blocks the change and explains that a credential is
   required first.

---

### User Story 3 - View current provider status (Priority: P2)

An admin needs to see, at a glance, which provider is currently powering
chat answers, so they can confirm a prior change took effect or diagnose
why chat behavior changed.

**Why this priority**: Supports the other two stories (you need to see the
current state to know whether your change worked) but has value even
without ever changing anything — e.g. confirming configuration after a
deployment.

**Independent Test**: As an admin, open the provider configuration page
with no changes pending and confirm it clearly shows which provider is
currently active.

**Acceptance Scenarios**:

1. **Given** a provider is currently active, **When** the admin opens the
   configuration page, **Then** the currently active provider is clearly
   indicated.

---

### Edge Cases

- What happens when a non-admin user attempts to view or change provider
  configuration? The request is rejected and no configuration details are
  revealed, consistent with this project's existing admin-only enforcement.
- What happens when the admin selects Bedrock but the deployment's
  underlying AWS credentials are missing or invalid? Saving the provider
  selection succeeds (this feature does not manage AWS credentials at all —
  see Assumptions); the resulting failure surfaces only when a chat request
  is actually attempted, as a chat-level error, not a configuration-page
  error.
- What happens when a saved API key is invalid or has been revoked by the
  provider? This is not detected at save time (out of scope); it surfaces
  only when a chat request using that provider fails.
- What happens when a saved model name doesn't actually exist for that
  provider (e.g. a typo, or a Bedrock model the AWS account doesn't have
  enabled)? Also not detected at save time — no live model-list lookup is
  performed against any provider — it surfaces only when a chat request
  using that provider and model fails.
- What happens when the admin tries to activate Bedrock without
  specifying a model identifier? The system blocks the change and
  explains that a model identifier is required first, mirroring the
  OpenAI-compatible credential requirement.
- What happens to a chat request that is already being generated at the
  moment an admin saves a different provider? It continues to completion
  using whichever provider was active when it started; only requests
  started after the save use the new provider.
- What happens if two admins change the configuration at nearly the same
  time? The later save wins; there is a single, global active-provider
  setting (not per-admin).
- What happens when an admin switches away from the OpenAI-compatible
  provider and later switches back to it? The previously saved base URL
  and key are still in place and do not need to be re-entered, unless the
  admin chooses to overwrite them with new values.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST allow an admin to view which chat-generation
  provider is currently active.
- **FR-002**: System MUST allow an admin to select a new active
  chat-generation provider from the supported set of providers.
- **FR-003**: System MUST support, at minimum, the following as selectable
  providers: Ollama, AWS Bedrock, and a generic OpenAI-API-compatible
  provider configured via a base URL plus an API key (covering OpenAI,
  Anthropic-compatible proxies, and other OpenAI-API-compatible services
  through a single integration rather than one integration per vendor).
- **FR-004**: For the OpenAI-compatible provider, system MUST allow the
  admin to enter and save a base URL, an API key, and a model name,
  together as one unit.
- **FR-005**: For AWS Bedrock, system MUST allow the admin to enter and
  save a model identifier to use for chat generation.
- **FR-006**: For Ollama, system MUST allow the admin to optionally enter
  and save a model name override; if left blank, chat generation MUST
  fall back to this project's existing default Ollama model setting.
- **FR-007**: System MUST persist the active provider selection, the
  saved OpenAI-compatible credential, the saved Bedrock model identifier,
  and any saved Ollama model override, such that they all survive a
  backend restart.
- **FR-008**: System MUST use the currently active provider — and its
  configured model — for every chat-generation request started after a
  configuration change is saved, with no code deployment or manual
  restart required.
- **FR-009**: System MUST restrict viewing and changing provider
  configuration to admin users only.
- **FR-010**: System MUST store the saved API key as plain text in the
  database, relying on this project's existing database access controls
  rather than application-level encryption — a deliberate choice (see
  Assumptions) consistent with no secret being encrypted at rest anywhere
  in this codebase today.
- **FR-011**: System MUST NOT display a previously saved API key's plain
  text value back to the admin after it has been saved; the configuration
  page MUST only indicate that a key is present (the saved base URL and
  model name MAY still be shown, since neither is a secret).
- **FR-012**: System MUST prevent an admin from activating the
  OpenAI-compatible provider until a base URL, a key, and a model name
  have all been saved for it, with a clear explanation of why the change
  was blocked.
- **FR-013**: System MUST prevent an admin from activating AWS Bedrock
  until a model identifier has been saved for it, with a clear
  explanation of why the change was blocked.
- **FR-014**: System MUST leave the embedding-generation provider setting
  (`settings.embedding_provider`) entirely unaffected by this feature —
  this feature governs chat-generation provider selection only.
- **FR-015**: System MUST retain the saved OpenAI-compatible credential
  and the saved Bedrock model identifier even after the admin switches
  the active provider away from them, so switching back does not require
  re-entering them.

### Key Entities *(include if feature involves data)*

- **Chat Provider Configuration**: The single, global setting describing
  which provider currently powers chat-generation, when it was last
  changed, the Bedrock model identifier to use when Bedrock is
  configured, and an optional Ollama model override (falls back to the
  existing default Ollama model setting when blank). Exactly one provider
  is active at a time.
- **Provider Credential**: The saved base URL, API key, and model name
  for the OpenAI-compatible provider, entered and stored together as one
  unit. A single global credential exists (not one per vendor); it
  persists independently of whether that provider is currently active.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An admin can change the active chat provider and have the
  very next chat request use it, with no deployment or manual restart
  involved.
- **SC-002**: 100% of chat-generation requests started after a provider
  configuration change use the newly active provider — none fall back to a
  previously active provider.
- **SC-003**: Non-admin users have a 0% success rate viewing or modifying
  provider configuration through any means the application exposes.
- **SC-004**: A previously saved API key's plain-text value is never shown
  back to any admin through the configuration page after the moment it was
  saved.
- **SC-005**: An admin who has never touched server configuration files or
  environment variables can, using only the admin panel, get a
  previously-unused OpenAI-compatible provider answering chat questions.
- **SC-006**: An admin can choose a specific model for Bedrock or the
  OpenAI-compatible provider and confirm chat answers are being generated
  by that exact model, without any code change.

## Assumptions

- Switching providers takes effect only for chat requests started after
  the save; it is not retroactive to in-flight requests.
- AWS credentials for the Bedrock provider are managed exactly as they are
  today (outside this application, via the deployment environment) — this
  feature only lets the admin pick Bedrock as active, it does not collect
  or manage AWS credentials itself.
- No live "test call" to a provider is required before allowing an API
  key or model name to be saved; validity of either is only discovered
  when a real chat request is made (matches the explicit scope boundary
  in the feature request) — this includes not verifying that a saved
  Bedrock or OpenAI-compatible model name actually exists or is
  accessible.
- The provider configuration is a single, global setting shared by all
  users of the chat feature — there is no per-user or per-conversation
  provider preference.
- Audit logging of who changed the provider and when is not required for
  this feature beyond what FR-001 (viewing current state) already provides;
  a full change-history view is out of scope.
- Ollama requires no credential at all to be selected active, consistent
  with its current zero-configuration usage in this codebase.
- The API key is stored as plain text in the database by explicit
  decision, not oversight: this project has no existing encrypted-secret
  mechanism to build on, and adding one (key management, rotation) was
  judged out of scope for this feature. This is a real production
  security tradeoff — access to the database is equivalent to access to
  the key — and should be revisited (e.g. application-level encryption
  using a dedicated key management approach) before this feature is relied
  upon with a production-grade provider credential.
- Only one API-key-based provider type (the generic OpenAI-compatible
  connection) is in scope; adding named, vendor-specific integrations
  (e.g. a dedicated Anthropic Messages API integration) is a future
  possibility, not part of this feature.
